# Анализ безопасности и архитектуры файлового менеджера (backend + frontend)

> Документ — **только анализ + целевая архитектура**. Кода не меняем (по требованию).
> Объекты: `app/packages/besnovatyj/yii2-cms-file/src/services/FileManagerService.php` (+ контроллёры),
> `app/packages/npm/filemanager-core/src` и их совместная работа.

## Context

Исходный триггер — вопрос «почему ФМ не обрабатывает ответ с `path:""`». Разбор показал, что это **не баг данных**, а
сознательная архитектура: сервер прячет реальный корень (`@static`) и отдаёт фронтенду **пути относительно realRoot**,
где `""` = публичный корень. Падает лишь клиентская валидация, запрещающая пустой `path`. Это вскрыло более важный
вопрос: насколько корректна и безопасна вся модель «фронтенд говорит виртуальными путями — бэкенд работает с ФС», и как
её довести до мульти-рут / мульти-адаптер (local + AWS S3 + FTP) дизайна.

---

## 1. Как это работает сейчас (контракт путей и сокрытие корня)

- `FileManagerService::__construct` фиксирует `realRoot = @static`, `baseUrl = @staticHostName` (
  `FileManagerService.php:29-34`).
- `getFolderDto($path)` маппит абсолютные пути в **относительные**: `mb_substr($file->getPath(), strlen($realRoot))` (
  `:90, :107`). Корень → `name='static'`, `path=''`. URL файла строится от `baseUrl` (статик-домен), а не от
  API-коннектора (`:111`).
- Фронтенд (`NavigationService.navigate(path)` → `backend.list({path})` → `mapDirDtoToFolderEntity`) кладёт результат в
  `FolderRegistry` по относительному пути; `key = path + '/' + name`.

**Вывод по контракту:** модель консистентна и реализует ровно то, что хочет пользователь — сокрытие корня. Пустой `path`
корня и пустой `path` его детей (`/cache`, `/origin`) корректны: `navigate('/cache')` → `realRoot.'/cache'` указывает на
реальную папку. Семантика **`'' = публичный корень`** (выбор пользователя) — верная и самодостаточная.

**Единственная нестыковка:** доменные сущности ядра (`FolderEntity.setPath` `FolderEntity.ts:51`, `fillFolders` `:118`,
`fillFiles` `:138`, `FileEntity.setPath`) бросают `AppError` на `path === ''`. Поэтому весь `list('/')` уходит в
`catch` → «Ошибка навигации». Это **client-side bug валидации**, а не проблема сервера.

## 2. Security-находки: BACKEND (ранжировано)

### 🔴 Критично

**2.1. Directory Traversal на `list` / `mkdir` / `upload` (рассинхрон защиты).**
Защита от обхода каталога (`realpath()` + `str_starts_with($real, $realRoot)`) реализована **только** в `deleteFile` (
`:470,479`), `deleteDirectory` (`:525,534`), `move` (источник, `:242-249`), `rename` (`:674,679`), `analyzeFile` (
`:804,811`). А вот:

- `getFolderDto` (`:38`): `$realPath = $realRoot . $path;` — только `str_starts_with($path,'/')` + `is_dir`.
  `path="/../../../etc"` → читает произвольный каталог (**чтение всей ФС, обход sandbox**).
- `uploadFile` (`:368`): `$realPath = $realRoot . $path;` + `is_dir` — запись загруженного файла в любой writable
  каталог.
- `createDir` (`:190`): `$realParent = $realRoot . $parentPath;` — создание каталога вне корня.

**2.2. Загрузка без валидации содержимого → потенциальный RCE/XSS.**
`uploadFile` (`:354-390`) не проверяет MIME (реальный, через finfo), размер, расширение. `getConfigDto` отдаёт
`allowedMimeTypes`, но это **нигде не enforced**. Можно залить `.php/.phtml/.htaccess` (RCE, если статик-домен исполняет
PHP) или `.svg/.html` (хранимый XSS на статик-домене). Имя санитайзится (`sanitizeName`), но не расширение/контент.

### 🟠 Высоко

**2.3. `move`: цель не конфайнится.** Источник проверяется на вхождение в `realRoot`, а `targetPath` — только
`is_dir($realRoot.$targetPath)` (`:251-253`), без `realpath`+confine. `targetPath="/../../tmp"` → вынос файла из корня.

**`2.4. Префиксная проверка без границы каталога`.** `str_starts_with($realPath, $this->realRoot)` (везде, где есть)
проходит для siblings: `realRoot=/var/www/static` ⊂ `/var/www/static-secret`. Нужно сравнивать с
`rtrim($realRoot, '/').DIRECTORY_SEPARATOR` либо канонизировать оба пути. Также `realRoot` сам не прогоняется через
`realpath()` в конструкторе → при симлинке сравнения ломаются.

**2.5. Утечка внутренней информации в ответах.** Контроллёр оборачивает исключения как
`ServerErrorHttpException($e->getMessage())` (`FileManagerController.php:64,86,...`). Доменные сообщения содержат пути;
`clearDir` бросает с **абсолютным** `$realPath` (`FileManagerService.php:582,587`). В проде (YII_DEBUG off) текст
HttpException показывается клиенту → раскрытие FS-layout. Нужен маппинг доменных ошибок в безопасные сообщения +
серверное логирование деталей.

### 🟡 Средне / низко

**2.6. Авторизация — только на уровне приложения.** Глобальный `as access` (`backend/config/main.php:83`,
`modules\user\components\AccessControl`, deny-by-default, allowlist логина/ошибок) прикрывает контроллёры. Но **сам
пакет не объявляет `behaviors()`/RBAC** — при переиспользовании вне этого backend ФМ окажется открытым. Нет гранулярных
прав (read vs write vs delete). Рекомендуется defense-in-depth: per-controller access + permission на
write/delete-операции.

**2.7. Нет ограничений на обход/размер.** `countChildDirs/countChildFiles` вызываются для каждого ребёнка в листинге (
`:60-62, :84-86`) → N+1 stat-штормы; `getDirSizeRecursive` (`:342`) безлимитный. На больших деревьях — DoS-вектор.
Рекомендуется кэш/ленивый подсчёт/пагинация.

**2.8. Симлинки/спец-файлы.** Листинг показывает `links`, но операции на них не нормализуют цель (TODO в `move/rename`
это признают). `clearDir` намеренно пропускает симлинки — но `deleteDirectory` через realpath может пройти по симлинку в
корень. Нужна явная политика по symlink/FOLLOW_SYMLINKS.

**2.9. SUA-коннектор — заглушка.** `service->sua()` (`:766`) возвращает хардкод-URL; `actionSuaConnector` (
`FileController.php`) лишь проверяет `isAjax`. При реализации обязан пройти ту же upload-политику (2.2).

**CSRF:** включён по умолчанию в backend; виджет шлёт `x-csrf-token`; `JsonParser` настроен. Похоже, покрыто — *
*проверить**, что `enableCsrfValidation` не отключён глобально для JSON.

## 3. Security-находки: FRONTEND и совместная работа

- **3.1. Жёсткая валидация ломает легитимные данные** (см. §1) — `path===''` отвергается. Concept-ошибка: пустой
  относительный путь — валиден.
- **3.2. Клиентская валидация загрузки отключена.** В `UploadService.upload` проверка несоответствия MIME есть, но
  `throw` **закомментирован** (`features/upload/model/UploadService.ts:73`) → невалидные файлы всё равно уходят на
  сервер. Это UX-, не security-контроль (авторитет — сервер), но сейчас не работает ни там, ни там.
- **3.3. Доверие к серверным метаданным.** Сущности тащат `permissions/isWritable/...`. Это можно показывать, но *
  *нельзя** использовать для клиентских «решений безопасности» (на бэкенде доверия фронту ноль — это правильно;
  зеркально фронт не должен полагаться на эти поля для контроля доступа).
- **3.4. Принцип «меньше знаний» соблюдён частично.** Хорошо: realRoot скрыт, фронт оперирует относительными путями. Но
  фронт видит абсолютные `url` (статик-домен) и FS-`permissions` — для будущих адаптеров (S3/FTP) часть этих полей
  бессмысленна/протекает. Стоит сузить DTO до необходимого.
- **3.5. `HttpClient` корректен** (CSRF-заголовки прокидываются, ошибки оборачиваются), но `toError` берёт
  `data.message` — а сервер туда кладёт внутренние сообщения (см. 2.5). После фикса сервера станет безопасно.

## 4. Целевая архитектура (multi-root / multi-adapter)

Цель: фронт шлёт запросы «как локальной ФС», бэкенд маршрутизирует на адаптеры (Local / S3 / FTP / …). Расширяемость и
безопасность — в основе.

### 4.1. Backend — слой хранилищ (ключевая структурная правка)

- **`VirtualPath` (value object)** — единая точка нормализации/валидации входящего относительного пути: запрет `..`,
  NUL-байта, backslashes, абсолютных путей; схлопывание слешей; пустой = корень. Используется **всеми** эндпоинтами →
  устраняет рассинхрон §2.1 одним местом. Это самый важный структурный фикс.
- **`StorageAdapterInterface`** (`list/stat/read/write/delete/move/rename/mkdir/exists/url`) поверх **виртуального**
  пути. Текущая SplFileInfo-логика → `LocalAdapter`. Дальше `S3Adapter`, `FtpAdapter`.
    - **Рекомендация:** взять **League\Flysystem v3** (есть Local/AWS-S3/FTP/SFTP, встроенная нормализация путей и
      защита от traversal — `PathTraversalDetection`). Комментарии в коде (Symfony Finder/Filesystem) показывают
      готовность к библиотеке. Это снимает локально-специфичный `realpath()`-подход, который для S3/FTP неприменим.
- **`StorageManager` / `MountRegistry`** — `mountId → {adapter, publicBaseUrl, права}`. Запрос несёт mount (префикс
  `/<mountId>/...` ИЛИ отдельное поле `storage`). `FileManagerService` становится тонким оркестратором: резолвит mount →
  делегирует адаптеру. **Никаких прямых FS-вызовов в сервисе.**
- **`UploadPolicy`** — в одном месте: реальный MIME через finfo по temp-файлу (не по присланному типу), max size,
  allow/deny расширений (блок `.php/.phtml/.htaccess`, sanitize/деактивация `.svg`), запись только через адаптер.
  Enforced **на сервере**, конфиг отдаётся клиенту лишь для UX.
- **Error mapping** — доменные исключения → безопасные коды/сообщения наружу; детали (пути) только в лог.
- **AuthZ** — `behaviors()`/RBAC на уровне пакета (read/write/delete как отдельные permissions), независимо от
  глобального `as access`.

### 4.2. Frontend — виртуальные пути + mount

- Сохранить контракт «фронт говорит относительными путями». **Принять `path=''` как корень** (релакс валидаторов
  `FileEntity`/`FolderEntity`; по решению пользователя — без нормализации, оставить `''`).
- Ввести понятие mount в `AppConfig`: `roots: [{id, label, defaultPath}]` (или single + опциональный mount).
  `NavigationState.path` → mount-квалифицированный (`{mountId, path}` или URI `mount://id/sub`). `FolderRegistry` уже
  хранит **Map корней** — расширить ключ до mount-qualified, чтобы исключить коллизии ключей между разными рутами.
- Все серверные данные — недоверенные: валидировать **форму/диапазоны**, не отвергать легитимные пустые значения; не
  принимать решений по `permissions`.
- Вернуть UX-валидацию загрузки (раскомментировать throw `UploadService.ts:73`), помня, что авторитет — сервер.

### 4.3. Совместный контракт (trust boundary)

- Версионированные DTO; граница доверия = «относительный виртуальный путь + mount + публичный url». Сервер канонизирует
  и конфайнит; клиент realRoot не видит.
- `url` файла — от публичной базы конкретного хранилища (статик-домен / S3 CDN), отвязан от API-коннектора (уже так —
  сохранить).

## 5. Дорожная карта (предложение, по приоритету)

1. **P0 (безопасность, точечно, без рефакторинга):** ввести `VirtualPath`-нормализацию и применить во **всех**
   эндпоинтах (`getFolderDto/uploadFile/createDir/move-target`); починить границу `str_starts_with` (+ `realpath`
   корня); enforce `UploadPolicy`; перестать отдавать внутренние сообщения наружу.
2. **P0 (frontend):** релакс валидации пустого `path` (даёт работающий ФМ на текущем сервере) — выбранная семантика
   `'' = корень`.
3. **P1 (архитектура):** вынести `StorageAdapterInterface` + `LocalAdapter` (предпочтительно Flysystem),
   `StorageManager`/mount; сервис → оркестратор. RBAC в пакете.
4. **P1 (frontend):** mount в `AppConfig`/`NavigationState`/`FolderRegistry`.
5. **P2:** S3/FTP-адаптеры; пагинация/ленивый подсчёт детей; политика symlink; реализация SUA по upload-политике.

---

## 6. Verification (как проверять при реализации)

- **Traversal:** запросы с `path` = `/../`, `/..%2f`, NUL, backslash, `/static-secret` → 4xx, без листинга/записи вне
  корня (юнит-тесты `VirtualPath` + интеграционные на каждый эндпоинт).
- **Upload-политика:** `.php`, `.svg`, mismatch MIME/расширение, превышение размера → отклонены сервером; легитимные
  изображения проходят.
- **Сокрытие корня:** в ответах нет абсолютных путей/realRoot; ошибки не содержат FS-layout (прод, YII_DEBUG=0).
- **AuthZ:** аноним и пользователь без права write/delete → запрет на mkdir/upload/delete/move/rename.
- **Контракт пустого пути:** `list('/')` отдаёт корень, фронт рендерит дерево; `navigate('/cache')` работает.
- **Multi-mount (после P1):** один и тот же относительный путь в разных mount не коллизится в `FolderRegistry`; операции
  уходят в правильный адаптер.

---

### Прямой ответ на исходный вопрос

ФМ не обрабатывает тот ответ, потому что ядро (`FileEntity`/`FolderEntity`) считает `path === ''` невалидным и бросает
`AppError`, тогда как сервер **намеренно** отдаёт `''` как публичный корень (сокрытие realRoot). Сервер прав, ядро —
нет. Это и есть точка релакса (P0-frontend), а заодно повод выстроить описанную выше mount/adapter-архитектуру.
