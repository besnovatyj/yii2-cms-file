## 2. Моя оценка исходников `yii2-cms-file` (текущее состояние)

### 2.1. Что сделано хорошо

- **Слой `src/storage/` — главное достижение.** `VirtualPath` (первый рубеж: запрет `..`, NUL,
  `\`), `StorageMount` (value object), `StorageMountFactory` (единственное место, знающее об
  адаптерах), `MountRegistry`, `StorageManager` (фасад). Ответственности разделены чисто, добавление
  FTP/SFTP действительно сведётся к одной ветке `match`.
- **Traversal закрыт системно.** Сравнение со старым кодом (`yii2-cms-file-before`) подтверждает:
  там `getFolderDto`/`createDir`/`uploadFile` склеивали `realRoot . $path` без confine (строки
  38/190/368), защита была только в delete/move-source/rename. Теперь все операции идут через
  Flysystem (нормализация + `PathTraversalDetected`) поверх `VirtualPath::parse()`. Рассинхрон
  защиты устранён архитектурно, а не точечными заплатками — правильное решение.
- `FileManagerService` стал адаптеро-независимым и компактным (492 строки против ~800 у старого),
  upload — потоковый (`writeStream`), метаданные синтезируются осмысленно (visibility → POSIX-mode).
- DI через `container.php` + `Module::setContainerConfig()` — декларативно, mounts с защитой от
  «битых» регистраций (zip — только при наличии файла, S3 — только при key+bucket).
- S3-параметры через модуль настроек (`options.php` → `params.s3`) с поддержкой S3-совместимых
  (endpoint, path-style) — соответствует принятой в проекте схеме конфигурирования.
- BC-виджет `Besnovatyj\File\widgets\CkeditorCustomWidget` — корректный тонкий шим (только
  преднастройка `$plugins`).

### 2.2. Проблемы, которые я нашёл сам (в заметках не отмечены или отмечены неточно)

1. ✅ ИСПРАВЛЕНО (шаг 3): **Устаревшие PHPDoc-ссылки на удалённый `StorageMount::path()`** — были
   в трёх местах (`FileManagerController`, `VirtualPath`, `PathTraversalException`). Докблоки
   переписаны на фактическую модель: первый рубеж — `VirtualPath::parse()`, второй — сам Flysystem
   (`PathNormalizer` → `PathTraversalDetected`).
2. ✅ ИСПРАВЛЕНО (шаг 3): **`rename()`: `oldName` не валидировался как одиночный сегмент** —
   склеивался в путь сырым, `oldName = "sub/file.txt"` позволял оперировать объектом вне заявленной
   родительской директории (в пределах mount — Flysystem конфайнит). Добавлен хелпер
   `assertSingleSegment()` (запрет `/`, `\`, NUL, `.`/`..`, пустого имени) → `DomainException` (422).
   У `createDir` имя фактически закрыто `sanitizeName` (заменяет `/` на `_`).
3. ✅ ИСПРАВЛЕНО (шаг 2): **Неконсистентные типы исключений**: `getFolderDto` бросал
   `yii\base\InvalidArgumentException`, остальные методы — `DomainException`. Унифицировано на
   `DomainException` вместе с введением error mapping в контроллёре.
4. **`composer.json`**: placeholder `"email": "your-email@example.com"`; захардкоженное поле
   `"version": "1.0.0"` (при доставке через git-теги его лучше убрать — классический источник
   рассинхрона тег↔манифест).
5. Мелочи: `sua()` — мёртвый `if (true)` (известная заглушка, TODO стоит); `getConfigDto()` отдаёт
   `fileMaxSize: ''` при заявленном на фронте `string|null`; для zip-mount `url()` с `baseUrl=''`
   даёт относительные URL (известно, отмечено в `_upd` §5 как отдельная задача
   download-эндпоинта).

### 2.3. Подтверждаю проблемы, отмеченные в заметках и всё ещё актуальные

- ✅ ИСПРАВЛЕНО (шаг 1, коммит `34a775e`): **Любая ошибка → HTTP 500.** Валидация запроса
  (разбор `VirtualPath`, проверки `isRoot()`, cross-mount) вынесена до `try`; добавлены хелперы
  `parsePath()` (`PathTraversalException` → 400) и `serviceFor()` (`UnknownMountException` → 404).
  В `delete` сервисы всех mount резолвятся до операций — неизвестный mount отклоняет весь батч
  до первого удаления.
- ✅ ИСПРАВЛЕНО (шаг 2): **Утечка внутренних сообщений**: введён error mapping через хелпер
  `execute()`: `DomainException` (бизнес-правило, сообщение адресовано пользователю, содержит
  только виртуальные пути) → 422 с сообщением + `Yii::warning`; прочие `Throwable`
  (инфраструктура/адаптеры) → 500 с нейтральным текстом, детали только в лог (`logException`).
- **AuthZ только глобальный `as access`**, в пакете нет `behaviors()`/RBAC — отложено, актуально.
- **Upload без контентной валидации** — осознанное решение (битые MIME у легитимных изображений),
  зафиксировано в memory проекта и в коде комментарием. Не считаю дефектом текущей стадии, но
  напомню: `.php/.svg/.html` на статик-домен — это хранимый XSS/RCE-вектор, и `UploadPolicy`
  остаётся самым важным незакрытым security-пунктом бэкенда.

## 5. Детальный анализ DTO-контрактов фронт↔бэк (парадигма «TypeScript-first»)

Зафиксированная парадигма (решение пользователя, 2026-06-09): **контракт в `ports.ts`/`dto.ts` —
источник истины**. Фронтенд — самостоятельный функциональный продукт, цепляемый к любому бэкенду;
подстроиться — задача бэкенда. Фронтенд в будущем будет логировать все свои действия, поэтому
бэкенд после каждой операции обязан возвращать **максимально полные данные** о совершённом или
неудавшемся действии. Фронтенд ожидает полные данные, но **не падает на базовом минимуме**.
Если фронт запрашивает данные и пока их не использует — это «функционал ещё не доделан», а не
повод урезать контракт.

Следствия для ревизии: (1) PHP приводим к TS-декларациям, а не наоборот; (2) сами TS-декларации
проверяем на соответствие парадигме — места, где контракт объявляет «не возвращай мне ничего»
(`move(): Promise<void>`) или несёт legacy-форму старого бэкенда (`RenameResponse` с комментарием
«Странная логика...»), противоречат ей и подлежат доработке на стороне TS; (3) поля «знаю, но
данных нет» кодируем как `null`, «бэкенд не поддерживает» — отсутствием опционального поля.

### 5.1. Пооперационный разбор

Формат: декларация TS → фактический ответ PHP → что фронт потребляет сегодня → целевое решение.

**list** — `ListResponse {path, item: DirDto}`.
PHP соответствует. Потребление: `NavigationService` → `mapDirDtoToFolderEntity(response.item)`.
Строгие валидаторы (`FileMeta` требует `mTime/aTime/permissions > 0`, `size >= 0`) бэкендом
удовлетворяются (синтез из visibility, шаг описан в `_upd` §3.3). Контракт менять не нужно.
Долги бэкенда в данных: `fileType` отдаётся плейсхолдером `'TODO - человекопонятный тип файла'` —
и это **видимый баг**: `PropertiesFeature:120` показывает `file.fileType` в свойствах файла
(«Тип»). `countChildDirs/Files = 0` — осознанная ленивая модель, но контракт это никак не
помечает; задокументировать в `dto.ts` («0 = не подсчитано»), иначе будущий UI нарисует «пусто».

**createDir** — декларация `Promise<FileDto>`.
PHP отдаёт FileDto-образную структуру, но `meta` — сокращённая (`FolderMetaDto`: без
`isWritable/isReadable/isExecutable/dimensions`), тогда как `FileDto.meta: FileMetaDto | null`.
Потребление: `CreateService.createFolder()` ответ **полностью игнорирует**. Решение (PHP):
отдавать полноценный `FileMetaDto` и для директорий (тот же синтез, что `fileMeta()`); это
единственное место, где «папка как FileDto» — легальная форма (`type: 'dir'`), и она обязана
нести полную meta. Контракт TS не меняется.

**rename** — декларация `RenameResponse {path, item: DirDto}` — **legacy-форма старого бэкенда**
(комментарий в `ports.ts`: «возвращает данные всей директории... Странная логика»; TODO в
`RenameFeature`: «в ответе должен быть статус операции»). PHP отдаёт одиночный FileDto.
Потребление: только `res.path` (для `nav:refresh`). Решение (TS + PHP): целевой контракт —
**операционный отчёт**:

```ts
export interface RenameResponse {
    ok: true;                 // неуспех приходит HTTP-ошибкой (422/5xx), не флагом
    path: string;             // виртуальный путь родительской директории
    oldName: string;
    newName: string;          // фактическое имя после санитизации на сервере
    item: FileDto;            // переименованный объект целиком (файл или папка type='dir')
}
```

`res.path` у фронта продолжает работать; для будущего лога действий есть всё. PHP: обернуть
текущий FileDto в отчёт (бэкенд уже знает oldName/safeNewName). Важно: `newName` в ответе может
отличаться от запрошенного (санитизация `sanitizeName`) — это фронту полезно знать и логировать.

**move** — декларация `move(): Promise<void>` — **прямо противоречит парадигме** («ничего не
рассказывай»). PHP отдаёт `{status:'ok'}`. Потребление: результат не используется, в
`MoveFeature` стоит TODO «Проверить успешность результата как-нибудь». Решение (TS + PHP):

```ts
export interface MoveResponse {
    ok: true;
    sourcePath: string;       // исходный виртуальный путь
    targetPath: string;       // виртуальный путь целевой директории
    item: FileDto;            // объект на новом месте (полная meta)
}
```

PHP: `move()` сервиса возвращает DTO перемещённого объекта (по образцу `rename()`), контроллёр
отдаёт отчёт вместо `{status:'ok'}`.

**delete** — `DeleteResponseDto.results[].type: 'file' | 'folder'` — PHP не кладёт `type` в обе
ветки неуспеха. Потребление: `delete.mapper` использует `path/ok/message` (`type` — пока нет).
Решение: тип объекта **знает только бэкенд**, поэтому поле обязано приходить всегда; для
несуществующего пути тип неизвестен → расширить контракт до `'file' | 'folder' | 'unknown'`
и обязать PHP заполнять его во всех ветках. Дополнительная находка (security, пропущена в
шаге 2): `deletePaths()` кладёт в `results[].message` сырой `FilesystemException::getMessage()` —
утечка внутренних сообщений адаптера в обход error mapping'а контроллёра (это per-item ошибки
внутри HTTP 200). Заменить на нейтральное сообщение + детали в лог.

**upload** — `UploadResponse {path, fileName}`; PHP отдаёт ещё `url` (в `ports.ts` комментарий
«можно добавить сюда»). Потребление: ответ не используется (UploadService сам эмитит
`upload:complete` из своих данных). Решение (TS + PHP): по парадигме — максимально полный отчёт:

```ts
export interface UploadResponse {
    path: string;             // куда загружен (виртуальный путь директории)
    fileName: string;         // фактическое имя после санитизации
    url: string | null;       // публичный URL (null — у mount нет публичной отдачи, напр. zip)
    item?: FileDto;           // полные метаданные созданного файла
}
```

PHP: `url` уже есть; `item` собрать через существующий `fileMetaFor()`. Бонус: фронт сможет
оптимистично класть файл в `FolderRegistry` без повторного `list`.

**analyze** — `FileAnalysisDto.exif?: Record<string,string>`; PHP отдаёт `exif: null`.
Потребление: `PropertiesFeature` передаёт результат в UI, `exif` пока не читается нигде.
Решение (TS): `exif?: Record<string, string> | null` — по принятой семантике `null` = «бэкенд
поле знает, данных нет», отсутствие = «не поддерживает». PHP не меняется. То же применить к
`audioTags`.

**config** — `GetConfigResponse {fileMaxSize: string|null, ...}` объявлен в `ports.ts`, но
**в интерфейсе `IFileManagerBackend` метода `getConfig()` нет** и `HttpFileManagerBackend` его
не реализует — PHP-эндпоинт `/config` фронтом не вызывается вовсе. Решение (TS): добавить
`getConfig(): Promise<GetConfigResponse>` в порт и backend (контракт уже описан — доделать
реализацию); PHP: отдавать `fileMaxSize: null` вместо `''` (текущая `''` — «ложь типа»:
строка есть, смысла нет).

### 5.2. Сквозные решения

1. **Форма отчёта мутирующих операций** (`rename`/`move`/`upload`/`createDir`): успех — полный
   отчёт с `item: FileDto`; неуспех — HTTP-ошибка (422 с доменным сообщением после шага 2), а не
   `ok: false`. Исключение — батчевый `delete`: там per-item статусы внутри HTTP 200 (уже так).
2. **Терпимость фронта к минимуму**: новые поля отчётов (`item`, `url`, `oldName`...) объявлять
   обязательными в TS можно только после того, как наш PHP их реально отдаёт; для чужих бэкендов
   зона терпимости — `null`/optional. Валидация формы ответов в рантайме (фронт не доверяет
   generic'ам `http.post<T>()`) — отдельная будущая задача (contract fixtures / lite-схемы).
3. **Утечки в per-item сообщениях** (delete) — бэкенд обязан применять ту же дисциплину
   error mapping, что и HTTP-слой: доменное → как есть, инфраструктурное → нейтрально + лог.

### 5.4 Мои (besnovatyj) замечания к принципу работы фронтэнда и планируемому функционалу

1) Фронтэнд должен в некоторой мере считать бэкэнд "тупым". Если бэкэнд после совершения запрошенной операции возвращает
   данные по которым фронтэнд может провалидировать совершенную операцию, то фронтэнд в будущем будет это делать
2) Предполагается возможность batch операций над файлами и папками (переименование, удаление, перемещение), это нужно
   учитывать при корректировке контрактов. Принцип предполагается аналогичный проводнику Windows. Напиши своё мнение по
   этому пункту, я сомневаюсь в необходимости реализации подобного функционала, боюсь переусложненной логики бэкэнда и
   взаимодействия бэкэнда с фронтэндом. Один из вариантов чрезмерного переусложнения - разные ограничения у разных
   mount.
3) Замечания по поводу получения конфигов с бэкэнда. Одним из разделов конфига может быть как раз получение возможностей
   предоставляемых бэкэндом. Как минимум разные возможности будут у адаптера для CKEditor 5 и standalone файлового
   менеджера, далее могут быть ограничения файловых систем или ограничения накладываемые разными mount (из чего сразу
   следует что задаётся общий конфиг и задаются конфиги по каждому mount). В конфиге обязательно должны быть ограничения
   на размер загружаемых файлов, у бэкэнда должна быть возможность передать фронтэнду ограничения по типам файлов или
   отсутствие данных ограничений. Конфиг будет расширяемый, эта та область, которую нельзя спроектировать сразу, в
   процессе развития файлового менеджера могут понадобиться данные конфигурации, которые сейчас нельзя предположить.

### 5.5. Мнение Claude по замечаниям §5.4

**По п.1 (бэкенд «тупой», фронт валидирует операции по ответу)** — согласен полностью, и
отчёт-форма контрактов из §5.1 спроектирована ровно под это. Один принцип стоит зафиксировать
явно: бэкенд в отчёте возвращает **факты после операции** (фактическое имя после санитизации,
фактический путь, meta объекта), а не эхо запроса. Тогда валидация фронта — это сравнение
«что просил» с «что получилось» (`newName !== requested` → имя было санитизировано, показать/
залогировать), и она не требует от бэкенда никакого «ума».

**По п.2 (batch-операции а-ля проводник Windows)** — ваши сомнения обоснованы, но вывод
предлагаю другой: **batch нужен, просто это фича фронтенда, а не бэкенда.**

Ключевое наблюдение: сам проводник Windows работает именно так — у файловой системы нет
«batch-API», проводник итерирует объекты по одному, показывает прогресс и per-item диалоги
конфликтов («заменить/пропустить/применить ко всем»). Эталонный UX достигается клиентской
итерацией поверх одиночных операций:

- **Бэкенд остаётся single-item** (атомарные `rename`/`move`/`mkdir`; `delete` уже батчевый —
  оставить как есть, удаление единственная операция, где серверный батч дёшев: нет семантики
  разрешения конфликтов, только per-item ok/fail).
- **Фронтенд получает `BatchOperationFeature`**: очередь per-item вызовов (последовательно или
  с ограниченной конкуренцией), модель прогресса (та же, что у `UploadService.uploadStatus` —
  паттерн в кодовой базе уже есть), политика ошибок («пропустить и продолжить» / «остановиться»,
  по образцу `DeleteResult {deleted[], failed[]}`).
- **Проблема «разные ограничения у разных mount» при этом исчезает из контракта**: каждая
  per-item операция валидируется бэкендом по правилам своего mount и возвращает свой 422; фронту
  не нужен «батчевый» протокол согласования ограничений. А capabilities из п.3 позволят ещё и
  заранее дизейблить недоступные действия.

Чего делать **не** стоит: серверные batch-эндпоинты для rename/move (транзакционность поверх ФС
всё равно не обеспечить — будут те же per-item результаты, но с усложнённым контрактом) и
cross-mount move как синхронная операция (это копирование потоков между адаптерами; текущий
явный отказ 400 — правильный; если когда-то понадобится — клиентский пайплайн read→upload→delete
или серверная async-задача, но не расширение CRUD-контракта). Единственный сценарий, где
серверный batch оправдан — тысячи объектов × сетевая латентность (массовые операции в S3), и
это решается отдельным механизмом «задача + poll», когда реально понадобится.

Итог: контракты §5.1 менять под batch не нужно — per-item отчёты и есть строительные блоки
батча. В TS можно сразу заложить только фронтовый тип `BatchResult<T>` (агрегат per-item
отчётов) — он серверного контракта не касается.

**По п.3 (конфиг как capabilities бэкенда)** — согласен, это правильное место для «разных
возможностей», и оно же закрывает заранее п.2 (ограничения mount). Предлагаемая структура:

```ts
export interface GetConfigResponse {
  contractVersion?: number;          // дешёвая страховка на будущее, с первого дня
  global: BackendCapabilities;       // дефолты для всех mount
  mounts?: Record<string, Partial<BackendCapabilities>>; // переопределения по mountId
}

export interface BackendCapabilities {
  upload?: {
    maxFileSize: number | null;      // БАЙТЫ; null = лимита нет (не string '2M' — парсинг
                                     // ini-нотации в байты — задача PHP, форматирование — UI)
    allowedMimeTypes: string[] | null;   // null = ограничений нет
    allowedExtensions?: string[] | null;
  };
  operations?: {                     // что mount умеет/разрешает; нет поля = разрешено
    upload?: boolean; mkdir?: boolean; delete?: boolean;
    rename?: boolean; move?: boolean;
  };
  publicUrls?: boolean;              // false = у файлов нет url (zip-mount сегодня!)
  readOnly?: boolean;                // сводный флаг для UI
}
```

Принципы, которые советую зафиксировать:
1. **Расширяемость — через optional-поля, а не `[key: string]: unknown`**: бэкенд вправе слать
   больше (структурная типизация фронта лишнее игнорирует), фронт типизирует поля по мере того,
   как начинает их использовать. Index-signature убила бы пользу типов.
2. **Слои не смешивать.** Различие «CKEditor-адаптер vs standalone ФМ» — это НЕ серверный
   конфиг, а режим встраивания: его задаёт хозяин-интеграция через `AppConfig` (адаптер передал
   `onSelect` → есть кнопка «вставить»). Бэкенд сообщает только то, что знает бэкенд: mounts,
   лимиты, операции. Итого три слоя: (1) `AppConfig` от интеграции, (2) `global` бэкенда,
   (3) per-mount переопределения. Бэкенд про CKEditor знать не должен.
3. **Enforcement остаётся на сервере**: capabilities — это UX-подсказки (задизейблить кнопку),
   последний рубеж — всё равно 422 на операции. Иначе появится соблазн «фронт проверил — сервер
   поверил».
4. Стартовый состав минимальный: `contractVersion`, `global.upload`, `publicUrls`/`readOnly`
   по mount (zip-mount сразу даст реальное применение). Остальное — по мере появления фич.

Влияние на план §5.3: в шаг 7а добавить порт `getConfig()` уже в этой структуре (вместо
плоского `GetConfigResponse`), в шаг 7б — PHP-реализация: `fileMaxSize` из ini-настроек в байтах,
`publicUrls: false` для mount с пустым `baseUrl`.

## 6. Журнал правок (фиксация по шагам)

- **Шаг 1** (коммит `34a775e`, `yii2-cms-file`): `FileManagerController` — корректные HTTP-статусы.
  Валидация запроса вынесена до `try`; хелперы `parsePath()` → 400 при traversal/NUL/`\`,
  `serviceFor()` → 404 при неизвестном mount; в `delete` неизвестный mount отклоняет весь батч
  до первого удаления. `catch (Throwable)` → 500 остался только вокруг файловых операций.
- **Шаг 2** (`yii2-cms-file`): error mapping + устранение утечки внутренних сообщений.
  Хелпер `execute()` в контроллёре: `DomainException` → 422 (сообщение пользователю, лог-warning),
  прочие `Throwable` → 500 «Внутренняя ошибка файловой операции» (детали только в лог).
  `FileManagerService::getFolderDto()`: `yii\base\InvalidArgumentException` → `DomainException`
  (унификация доменных ошибок, иначе «директория не существует» стала бы нейтральным 500).
  Контракт для фронтенда: «не найдено/уже существует/некорректное имя» теперь приходят как 422
  с прежним текстом в `message`; нейтральный 500 — только для настоящих внутренних сбоев.
- **Шаг 3** (`yii2-cms-file`): comment rot + контракт `rename`.
  Переписаны три устаревших PHPDoc, ссылавшихся на удалённый `StorageMount::path()`
  (`FileManagerController`, `VirtualPath`, `PathTraversalException`) — теперь описывают фактические
  рубежи защиты (`VirtualPath::parse()` + Flysystem `PathNormalizer`).
  `FileManagerService::rename()`: `oldName` валидируется хелпером `assertSingleSegment()`
  (запрет `/`, `\`, NUL, `.`/`..`, пустого имени) — имя обязано быть одиночным сегментом внутри
  `parentPath`, а не путём.
- **Шаг 4** (`npm/filemanager-core`): `AppRuntime` — window-listeners error boundary
  (`error`, `unhandledrejection`) вынесены в стабильные поля-стрелки и снимаются в `destroy()`
  (закрыт TODO на строке 108); `destroy()` стал идемпотентным (флаг `destroyed`) — его вызывают
  и обработчик `fm:close`, и внешний владелец (CKEditor-адаптер), раньше это давало двойной
  `widget.destroy()`. ⚠️ Требуется пересборка dist ядра и адаптера (адаптер бандлит ядро);
  разумно сделать один раз после шагов 5–6.
- **Шаг 5** (`npm/filemanager-core`, коммит `89e933f`): lifecycle-утечки listeners.
  `DirectoryContentFeature`: подписки `navState`/`registry`/`selectionStore` теперь кладутся в
  `unsubs` (раньше их `Unsubscriber` терялись); DOM-обработчики переведены в поля-стрелки —
  `add/removeEventListener` получают одну ссылку (раньше пары делали разные `bind(this)`, отписка
  снимала «не тот» обработчик). `SplitPanelWC`: `pointerdown` биндится один раз, у поля-стрелки
  `handleResize` убран лишний `bind`; регистрация слушателей вынесена из-под guard'а `shadowRoot` —
  disconnect/connect симметричны (повторное подключение элемента к DOM восстанавливает слушатели).
  dist по-прежнему не пересобран (после шага 6).
- **Шаг 6** (`npm/filemanager-core` `98d06cf` + `ckeditor5-filemanager` `6921d0e`): инкапсуляция
  закрытия ФМ. В `AppRuntime` добавлен публичный `close(source = 'external')` — эмитит `fm:close`,
  то есть проходит ту же единственную точку уничтожения, что крестик/Esc/overlay. Адаптер в обоих
  местах переведён с `runtime['bus']` (доступ к private-полю строковым индексом) на
  `runtime.close('select')`.
  ⚠️ **Пересборка dist (шаги 4–6)**: адаптер typecheck'ается против установленного из npm
  `filemanager-core@1.0.0`, в котором `close()` ещё нет. Порядок: (1) в core — `npm run build` +
  `npm run types`, поднять версию (1.0.1) и опубликовать в npm (либо временно вернуть
  `file:../../npm/filemanager-core` в адаптере); (2) в адаптере — обновить зависимость,
  `npm install && npm run build` (+ `types`); (3) закоммитить dist обоих пакетов.
- **Шаг 7а** (`npm/filemanager-core`, коммит `4ec2682`): ревизия контрактов API по §5
